# 0090. 変換の計算を減らす(下書きで確かめる生成・LLM の先行採点ほか)

- 状態: 採用
- 日付: 2026-11-25
- 関係: docs/adr/0024(GPU のない PC)、0033(前置きの共有)、0088(CUDA)、0089(軽い打ち間違いの補正)

## 背景

利用者(2026-11-25): 精度を保ったまま、動作(待ち時間・負荷)を大きく軽くする。2026-11-10 の「AI の計算は省かない
(ビームの本数・生成の長さは減らさない)」(0088)は守る。

1,032 問の変換の内訳(RTX 3060、Vulkan、中央値): genmai の生成 112 ms(全体の 54%)、LLM の採点 39 ms(29%)、
zenz の採点 15 ms。生成は約 20 ステップで、1 ステップの時間は小さな計算を呼ぶ回数で決まる(0088)。

## 決めたこと

1. **下書きで確かめる生成**(`ZenzScorer::DraftedBeamSearch`)。ラティスの文と前の打鍵の生成結果を下書きにし、計算する
   ビームの後ろに下書きの続き(既定 10 トークン、`KOTORI_LM_DRAFT`)を並べて 1 回で計算する。ビームが下書きどおりに
   伸びたステップは GPU を呼ばない。選び方はふつうのビームサーチと同じなので、結果は変わらない(入れ替わり 0)。
2. **LLM の先行採点**: 生成の間に、ラティスの文を別のスレッドで LLM に採点させる(LLM は生成と別のモデル)。後の
   採点では済んだ文を採点し直さない(`KOTORI_LM_PRESCORE=0` で使わない)。
3. **計算しなくてよいものを外す**: 採点の木の葉(子のない節)を計算に入れない。コピー癖の確かめの LLM の採点
   (`ScoreIsolated`)は、前の文の KV を消さない。
4. **Flash Attention を既定で有効**(入れ替わり 0、-3%)。まとめて計算するスレッドは物理コアの数。
   `LogSumExp` は AVX2(足す値と順は同じ)。
5. 体感の引っかかり: 待ちのポーリングを高分解能タイマーに(Windows の 15.6 ms の丸めをなくす)、状態ファイルの
   書き込みをモデルのロックの外に、候補の窓の裏の画面を使い回す、前の文を読むのが遅いアプリでは読む長さを縮める。

6. **2 段階の読み込み**(Phase 5-1): 起動・休みからの戻りでは、zenz を開いたら AI の変換を始め(`loading_` を下ろす)、
   LLM はモデルのロックの外で開いてから差し込む。LLM を開いている間の変換は LLM なしの AI で出す(それまでは AI なし)。

## 採らなかったもの

- KV を q8_0 にする: 遅くなり(中央値 +3 ms)、入れ替わる(直った 5・外れた 3)。
- LLM を小さく・低いビットにする(Qwen2.5-0.5B、sarashina2.2-0.5B、TinySwallow の IQ4〜Q2): 速くならず、精度が下がる。
- LLM を使わない: 906 → 882/1033。
- 高い確信のときに LLM を省く(`KOTORI_LM_SKIP_LLM_MARGIN=3`): 開発用では下がらず -4% だが、判定用で 838 → 836/960
  (同乗→同情、JavaScript→ジャバスクリプト)。既定では使わない。
