# 0088. NVIDIA の GPU で CUDA 版の計算を使う(追加パッケージ)

- 状態: 採用(2026-11-10。最初は不採用にしたが、呼び出しの形をそろえて測り直し、利用者が採用を決めた)
- 日付: 2026-11-10
- 関係: docs/adr/0016(llama.cpp の公式ビルドを同梱する)、0024(GPU の選び方。CUDA を見送った理由)、
  0078(内蔵 GPU)、0085(genmai)、0086(追加の AI のダウンロード)

## 背景

利用者(2026-11-10): 変換と起動を速くしたい。ただし AI の計算は省かない(ビームの本数・生成の長さは減らさない)。

起動の遅れ(モデル全体の SHA-256)は別に直した。変換(Space)は中央値で約 170 ms かかり、その大半は genmai の生成だった。
RTX 3060・b11259(Vulkan)で測った内訳は次のとおり。

- 1 回の変換のうち約 100 ms は、生成の約 20 ステップ。1 ステップでは、genmai と追加の生成器
  (zenz-v2.5-native-generator)が、それぞれ 8 本の候補を 1 トークンずつ伸ばす。2 つは同時に動かしている。
- 生成の間、GPU はほぼ埋まっていて、CPU 側の待ちは 2 ms ほどしかない。
- genmai の 1 ステップ 5.4 ms のうち 4.2 ms は、8 列の行列×ベクトル積(q8_0、MMVQ)。実効の帯域は約 60 GB/s で、
  RTX 3060 の帯域(約 360 GB/s)を大きく下回る。1 ステップで約 400 回の小さな計算を呼ぶ。
- Vulkan のままでは縮める余地がほとんどない。Flash Attention、`GGML_VK_*` の切り替えでは速くならず、
  9 トークン以上の行列積の経路を使わせても 5% しか縮まない。

llama.cpp の CUDA 版は、1 ステップの計算をまとめて GPU に渡す仕組み(CUDA グラフ)と、NVIDIA 向けに調整した計算を持つ。

## 制約

- 本体の MSI はすでに 1.59 GiB(上限 1.8 GiB。0086)。CUDA 版の DLL(約 0.7〜1.1 GB)は入らない。
- CUDA の実行時ライブラリ(cudart・cuBLAS)は OSS ではない(NVIDIA の CUDA EULA で再配布を認められた部品)。
- NVIDIA 以外の GPU(AMD・Intel)と、ドライバーの古い PC では使えない。Vulkan 版は残す。
- 0086 のダウンロードは、データ(モデル)をユーザーのプロファイルに置く仕組み。実行されるコード(DLL)を、
  利用者が書き込めるフォルダに置いて変換サーバーに読み込ませる用途は想定していない。

## 選択肢

| | 置き場所 | 本体の MSI | よい点 | 問題 |
| --- | --- | --- | --- | --- |
| A. 本体の MSI に同梱 | インストール先 | 約 2.3 GiB | 何もしなくても速い | 上限を超えるので作れない |
| B. **別の MSI(追加パッケージ)** | インストール先の `cuda\` | 変わらない | 管理者権限で、書き込めないフォルダに入る。本体と別に入れたり外したりできる | 配布物が 1 つ増える |
| C. 設定画面からダウンロード(0086 の仕組み) | ユーザーのプロファイル | 変わらない | 入れる手順が簡単 | 利用者が書き込めるフォルダの DLL を読み込む。読み込むたびに約 0.7 GB を確かめないと差し替えを防げず、直したばかりの起動の遅れが戻る |
| D. CUDA を使わない | — | 変わらない | 何も増えない | 変換は約 170 ms のまま |

## 決定

**B(別の MSI の追加パッケージ `AsteriaCuda64.msi`)** にする。

1. **中身**(`mozc/cuda-addon/build_addon.ps1`、`AsteriaCuda.wxs`)
   - b11259 の公式 CUDA 13.4 版から `ggml-cuda.dll` と、cudart・cuBLAS の DLL(合わせて約 0.7 GB)だけを取る。
     zip は版と SHA-256 を固定する。`llama.dll` と `ggml-base.dll` は本体のものを使う。
   - 13.4 にした理由:12.4 より DLL が 0.4 GB 小さく、速さはほぼ同じ(12.4 は約 1.14 GB)。13.x は
     ドライバー 580 以降と Turing(RTX 20)以降の GPU が要る。それより古い PC は Vulkan のまま動く。
   - 版の札 `asteria-cuda.txt`(`llama=b11259`)と、ライセンスの表示 `NOTICE-cuda.txt` を添える。
   - MSI の版は `1.<作り直しの回数>.<llama.cpp の版の番号>`。本体のリリースごとに同じものを作って添付する。
2. **入れる場所**:本体と同じ `Program Files (x86)\Asteria` の `cuda\`(管理者権限でしか書き込めない)。
   本体が入っていないときは入れない(本体の UpgradeCode を探す)。
3. **読み込み**(`rewriter/llama_runtime.cc`)
   - 本体の DLL を読んだ後、`cuda\asteria-cuda.txt` の版が本体の llama.cpp の版(`kLlamaBuild`)と同じときだけ、
     `cuda\ggml-cuda.dll` を `LoadLibraryExW`(同じフォルダの依存を探す)で読み、`ggml_backend_load` で登録する。
   - 札がない・版が違う・読めない(ドライバーが古い、NVIDIA の GPU がない)ときは何もしない。それまでどおり Vulkan で動く。
   - `KOTORI_LM_CUDA=0` で使わない(比べるため)。
4. **GPU の選び方**(`LlamaGpuDevice`)
   - 同じ GPU が CUDA と Vulkan の両方に出るので、メモリの差が 1 GiB 以内なら CUDA を選ぶ。別の GPU なら、
     これまでどおりメモリの大きい方を選ぶ。選ぶのは 1 台だけ、という 0024 の決まりは変えない。
   - 設定画面の AI の状態は「GPU: NVIDIA GeForce RTX 3060 (CUDA)」のように出す。
5. **呼び出しの形をそろえる**(`ZenzScorer::BeamSearch`)
   - b11259 の CUDA 版は CUDA グラフをコンテキストごとに 1 つしか持たず、トークンの数が変わるたびにグラフなしで
     動かしてから作り直す(最新の llama.cpp でも同じ)。1 回の変換で形はたびたび変わるので、そのままでは
     速いのは 8 トークンの続きだけで、変換全体は 8〜10% しか縮まなかった。
   - CUDA のときは、生成器への呼び出しをすべて 8 トークン・8 出力にする。ビームの終わりで足りない分は、
     今の組で使っていないビームのシーケンスに捨てるトークンを足す。長い前置きは 8 ずつに分ける。
   - 足した分の計算は増える(トークン数で約 9%)が、ビームの本数と生成の長さは変えない。
   - Vulkan では遅くなる(中央値 181 → 197 ms)ので使わない。`KOTORI_LM_FIXED_BATCH=N` で数を変えられる(0 で使わない)。
6. **ライセンス**:`docs/licenses.md` と追加パッケージの `NOTICE-cuda.txt` に、CUDA の実行時ライブラリ
   (NVIDIA CUDA EULA で再配布を認められた部品)を書く。

C は採らない。読み込むたびに約 0.7 GB の DLL を確かめると起動の遅れが戻り、確かめずに読み込むと、
利用者が書き込めるフォルダのコードを変換サーバーに読み込ませることになる。

## 結果(2026-11-10、docs/verification/cuda-backend-20261110.md)

- アプリでの変換(日常 40 問、交互に 3 回):中央値 Vulkan 181〜185 ms → CUDA 137 ms(**−25%**)、
  p95 257〜262 → 198〜199 ms。そろえないままの CUDA は −8〜−10% だった。
- AI の準備は約 1.0 秒で変わらない。GPU のメモリは 2324〜2364 → 2277 MB、プロセスのメモリは約 3.0 → 3.3 GB。
- 精度(Standard、`eval_baseline.py`):AJIMEE 189 → 188/200、文脈の選択(判定用)228 → 226/300、
  日常 78 → 79/81、打ち間違い・慣用句・ニュアンスは同じ。下がった 3 問は、仮名と漢字の表記の選び方
  (ユリ/百合、うまく/上手く、結構/けっこう)。そろえないままの CUDA でも同じ問が変わったので、
  CUDA の計算の順番の違いによるもので、そろえたことによるものではない。
- 採用の条件は、最初は「中央値 30% 以上、下がるセットがない」とした。結果は −25%、下がった問は 95% 区間の
  中の 1〜2 問だった。利用者がこの結果で採用を決めた(2026-11-10)。

## 残すこと

- 設定画面の「NVIDIA の高速化を使う」は作っていない。止めるには追加パッケージを外す(アプリと機能)。
- 追加パッケージを入れた後・外した後は、変換サーバーが次に起動したとき(サインアウトなど)から変わる。
- CI の Windows には GPU がないので、CUDA で動くことはこの開発 PC でだけ確かめた。読み込めないときの経路
  (札なし・版違い・`KOTORI_LM_CUDA=0`)も手元で確かめた。
- llama.cpp を上げるときは、`build_addon.ps1` の版・URL・SHA-256 と `kLlamaBuild` を一緒に変え、同じ手順で測り直す。
  llama.cpp の CUDA 版が形ごとに複数のグラフを持つようになれば、呼び出しをそろえる処理は要らなくなる。

## 採らない案

- **Vulkan の調整だけで済ませる**:上の背景のとおり、縮むのは 5% 程度。
- **ビームの本数や生成の長さを減らす**:結果が変わり、「AI の計算を省かない」に反する。
- **ggml-cuda を自分で作り直して、形ごとにグラフを持たせる**:CUDA Toolkit のビルドを CI に足し、
  llama.cpp を上げるたびに変更を保ち続けることになる。呼び出しをそろえれば公式の DLL のままで済む。
- **採点(zenz・LLM)の呼び出しもそろえる**:長さが毎回違う(55〜135 トークン)ので、そろえると計算が大きく増える。
