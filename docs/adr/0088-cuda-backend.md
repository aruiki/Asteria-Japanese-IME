# 0088. NVIDIA の GPU で CUDA 版の計算を使う(不採用)

- 状態: 不採用(2026-11-10 に測った。下の「結果」。条件 1 を満たさないので D「CUDA を使わない」にする)
- 日付: 2026-11-10
- 関係: docs/adr/0016(llama.cpp の公式ビルドを同梱する)、0024(GPU の選び方。CUDA を見送った理由)、
  0078(内蔵 GPU)、0085(genmai)、0086(追加の AI のダウンロード)

## 背景

利用者(2026-11-10): 変換と起動を速くしたい。ただし AI の計算は省かない(ビームの本数・生成の長さは減らさない)。

起動の遅れ(モデル全体の SHA-256)は別に直した。変換(Space)は中央値で約 170 ms かかり、その大半は genmai の生成だった。
RTX 3060・b11259(Vulkan)で測った内訳は次のとおり。

- 1 回の変換のうち約 155 ms は、生成の約 20 ステップ。1 ステップでは、genmai と追加の生成器
  (zenz-v2.5-native-generator)が、それぞれ 8 本の候補を 1 トークンずつ伸ばす。2 つは同時に動かしている。
- 1 ステップ約 8 ms のうち、GPU が動いているのは約 7.1 ms(genmai 5.4 ms、追加の生成器 1.7〜2.2 ms。
  `GGML_VK_PERF_LOGGER`)。GPU はほぼ埋まっていて、CPU 側の待ちはほとんどない。
- genmai の 5.4 ms のうち 4.2 ms は、8 列の行列×ベクトル積(q8_0、MMVQ)。実効の帯域は約 60 GB/s で、
  RTX 3060 の帯域(約 360 GB/s)を大きく下回る。1 ステップで約 400 回の小さな計算を呼び、1 回ごとに 2 µs 以上かかる。
- Vulkan のままでは縮める余地がほとんどない。
  - Flash Attention、`GGML_VK_*` の切り替え(MMVQ、整数積、結合、グラフ最適化)では速くならない。
  - 9 トークン以上の行列積の経路を使わせても、1 回の変換で約 8 ms(5%)しか縮まない。
  - 最新の b12244 でも、NVIDIA で小さいバッチのときの経路の選び方は変わっていない。

時間の大半は、小さな計算を毎回呼び出す手間と、小さいバッチ向けの計算の効率で決まっている。llama.cpp の CUDA 版は、
1 ステップの計算をまとめて GPU に渡す仕組み(CUDA グラフ)と、NVIDIA 向けに調整した計算を持つ。0024 では、LLM について
Vulkan の 1.5〜2 倍の速さと測った。そのときは DLL が約 1.1 GB で MSI に入らないので見送った。

## 制約

- 本体の MSI はすでに 1.59 GiB(上限 1.8 GiB。0086)。CUDA 版の DLL は入らない。
- 公式の b11259 の CUDA 版は、`llama-b11259-bin-win-cuda-12.4-x64.zip`(252 MB)と
  `cudart-llama-bin-win-cuda-12.4-x64.zip`(373 MB)。13.4 版はそれぞれ 146 MB と 404 MB(いずれも圧縮時)。
  展開すると cuBLAS を含めて約 1 GB になる。
- CUDA の実行時ライブラリ(cudart・cuBLAS)は OSS ではない(NVIDIA の CUDA EULA で再配布を認められた部品)。
- NVIDIA 以外の GPU(AMD・Intel)と、ドライバーの古い PC では使えない。Vulkan 版は残す必要がある。
- 0086 のダウンロードは、データ(モデル)をユーザーのプロファイルに置く仕組み。実行されるコード(DLL)を、
  利用者が書き込めるフォルダに置いて変換サーバーに読み込ませる用途は想定していない。

## 選択肢

| | 置き場所 | 本体の MSI | よい点 | 問題 |
| --- | --- | --- | --- | --- |
| A. 本体の MSI に同梱 | インストール先 | 約 2.6 GiB | 何もしなくても速い | 上限を超えるので作れない |
| B. **別の MSI(追加パッケージ)** | インストール先の `cuda\` | 変わらない | 管理者権限で、書き込めないフォルダに入る。本体と別に入れたり外したりできる | 版を本体と合わせる必要がある。配布物が 1 つ増える |
| C. 設定画面からダウンロード(0086 の仕組み) | ユーザーのプロファイル | 変わらない | 入れる手順が簡単 | 利用者が書き込めるフォルダの DLL を読み込む。読み込むたびに約 1 GB を確かめないと差し替えを防げず、直したばかりの起動の遅れが戻る |
| D. CUDA を使わない | — | 変わらない | 何も増えない | 変換は約 170 ms のまま |

## 提案

**B(別の MSI の追加パッケージ)** にする。中身と働きは次のとおり。

1. **中身**
   - b11259 の公式 CUDA 版から `ggml-cuda.dll` と、それが使う cudart・cuBLAS の DLL だけを取る。`llama.dll` と
     `ggml-base.dll` は本体のもの(Vulkan 版と同じ固定ソース)を使う。
   - どちらの CUDA 版(12.4 か 13.4)にするかは、下の「判断の前に測ること」4 で決める。
   - 取得する zip は、0016 と同じく版と SHA-256 を固定する。
2. **入れる場所**:インストール先の `cuda\`(管理者権限でしか書き込めない)。本体の MSI と同じ版の番号を持ち、
   本体の版と合わないときは読み込まない(`ggml-cuda.dll` は同じ版の `ggml-base.dll` に合わせて作られているため)。
3. **読み込み**(`EnsureLlamaRuntime`)
   - いまの `ggml_backend_load_all_from_path(インストール先)` の前に、`cuda\` があれば `ggml-cuda.dll` を読み込む。
   - 読み込めない(ドライバーが古い、NVIDIA の GPU がない)ときは何もしない。それまでどおり Vulkan で動く。
4. **GPU の選び方**(`LlamaGpuDevice`)
   - 同じ GPU が CUDA と Vulkan の両方に出るので、使える CUDA の機器があれば、それを優先する。
   - 選ぶのは 1 台だけで、モデルをほかの機器に分けない、という 0024 の決まりは変えない。
   - 選んだ機器の種類(CUDA / Vulkan)を状態ファイルと設定画面に出す。
5. **戻す手段**:設定に「NVIDIA の高速化を使う」を置く(既定オン、追加パッケージを入れたときだけ表示)。
   オフにすると、次に読み込むときから Vulkan に戻る。
6. **ライセンス**:`docs/licenses.md` と NOTICE に、CUDA の実行時ライブラリ(NVIDIA CUDA EULA、再配布できる部品の一覧)を
   追記する。追加パッケージのインストーラーでも示す。

C は採らない。読み込むたびに約 1 GB の DLL を確かめると、直したばかりの起動の遅れが戻る。確かめずに読み込むと、
利用者が書き込めるフォルダのコードを変換サーバーに読み込ませることになる。

## 判断の前に測ること(採用の条件)

この開発 PC(RTX 3060)で、追加パッケージを作る前に公式の CUDA 版で測る。

1. **速さ**
   - `llama-batched-bench` で、genmai と追加の生成器の 1 ステップ(共通の前置き 17、8 本)を Vulkan と比べる。
   - アプリの計測(`bench.py async`、新旧を交互に 3 回)で、変換の中央値と p95 を比べる。
   - 中央値が **30% 以上** 縮まなければ採らない(D にする)。
2. **精度**
   - 計算の順番が変わるので、結果は Vulkan と完全には一致しない。
   - 開発用・判定用の文脈の選択(297)、打ち間違い(40)、AJIMEE で、**下がるセットがない** ことを確かめる。
3. **GPU のメモリ**
   - CUDA は機器ごとに数百 MB を余分に使う。
   - Standard(約 2.3 GB)と Unreal(8 GB の判定役)で、VRAM 8 GB の PC に収まるかを確かめる。
   - 収まらない段階では Vulkan に戻す。
4. **起動**
   - cuBLAS の読み込みで、AI の準備ができるまでの時間がどれだけ延びるかを測る(いまは 0.9 秒)。
   - 12.4 版と 13.4 版で、速さ・起動・必要なドライバーを比べ、どちらにするか決める。
5. **戻り**:CUDA の読み込みに失敗する PC(ドライバーが古い、NVIDIA 以外)で、Vulkan のまま変わらず動くことを確かめる。
   CI の Windows には GPU がないので、読み込めないときの経路は単体試験で確かめる。

## 結果(2026-11-10、docs/verification/cuda-backend-20261110.md)

- 1 ステップだけを測ると、genmai の 8 本は 5.77 → 3.3〜3.6 ms(約 40% 速い)。
- アプリでの変換の中央値は、Vulkan 約 168 ms → CUDA 13.4 約 154 ms・12.4 約 151 ms(−8〜−10%)。**条件 1(30% 以上)を満たさない**。
- 縮まない理由:b11259 の CUDA 版は、グラフをコンテキストごとに 1 つしか持たず、呼び出しの形が変わるたびにグラフなしで動かして
  作り直す。1 回の変換で形はたびたび変わる(ビームの始めと終わり、前置き、採点)ので、速いのは 8 トークンの続きだけになる。
  1 トークンや採点の呼び出しは、かえって Vulkan より遅い。
- GPU のメモリは 2324 → 2277 MB、AI の準備は同じ程度だった(DLL を初めて読むときだけ 12.4 で約 7 秒)。
- 精度は、速さの条件を満たさなかったので測っていない。
- 下の「メンテナに決めてほしいこと」は、不採用にしたので答えなくてよい。llama.cpp を上げるときに、同じ手順で測り直す。

## メンテナに決めてほしいこと(不採用にしたので不要)

- 配布物を 1 つ増やしてよいか(B)。本体の MSI に入らない以上、A は選べない。
- 本体と追加パッケージの版の合わせ方:同じリリースに両方を載せるか、追加パッケージは llama.cpp を上げたときだけ作り直すか。
- CUDA の実行時ライブラリ(OSS でない部品)を配布物に入れてよいか。

## 採らない案

- **Vulkan の調整だけで済ませる**:上の背景のとおり、縮むのは 5% 程度。
- **ビームの本数や生成の長さを減らす**:結果が変わり、「AI の計算を省かない」に反する。
- **ggml-vulkan を自分で作り直して計算を調整する**:Vulkan SDK とシェーダーのビルドを CI に足す必要がある。
  llama.cpp を上げるたびに調整を保ち続けることにもなる。調整しても、呼び出しの手間は残る。
