# 0074. 打ち間違いを、打ったキーの単位と複数か所で直す

- 状態: 採用
- 日付: 2026-10-26
- 関係: docs/adr/0036(打ち間違いの補正)、0067(AI の結果を待って候補を出す)、0071(手が止まった間の計算)
- 検証: [docs/verification/key-typo-correction-20261026.md](../verification/key-typo-correction-20261026.md)

## 背景

利用者が、直してほしい打ち間違いの例を 5 つ示した(`eval/sets/asteria-typo-keys-20261026.json`)。

| 打ったキー | 正しい文 | v3.0.0 の 1 番目の候補 |
| --- | --- | --- |
| ko-hi-wotyuusitusuru | コーヒーを抽出する | コーヒーを注湿する |
| makotonihitureisimasita | 誠に失礼しました | 誠に筆礼しました |
| hoikuennniomukainiikanaito | 保育園にお迎えに行かないと | 保育園にお向かいに行かないと |
| kyougakkuniikanaiikenakattanoninazekakyuukouninatteuesiina | 今日学校に行かないといけなかったのになぜか休校になってうれしいな | 今日学区に行かない行けなかったのに何故か休校になって嬉しいな |
| tuzukiwosuru | 続きをする | つづきをする |

ADR0036 の補正は、読みのかなを 1 か所だけ決まった型(濁点、あ行の子音の抜け、母音、う・い・ん・っ の抜けなど)で
書き換え、辞書の語で区切ったコストが下がったものを試す。5 例は 1 つも直せなかった。調べると理由は 3 つあった。

- 打ち間違いはキーの単位で起きる。gakkou の o が抜けると「がっこう→がっく」になり、かなの 1 か所の書き換えにならない。
- 子音の打ち違い(し→ひ)、ず/づ、拗音の抜け(しゅつ→しつ)は、書き換えの型にない。
- 辞書のコストは、打ち間違いの読みも短い語で区切れる(ちゅう+しつ、つ+ずき)うえ、「がっく(学区)」のように
  実在の語になる打ち間違いでは下がらないので、正しい直しを選べない。

## 決めたこと

GPU で LLM を使うとき(Standard 以上)、ADR0036 の補正を次のように広げる(`rewriter/lm_rewriter.cc`)。

1. 書き換えの種類を増やす。
   - キーの単位: 打ったローマ字(`ComposerData::GetRawString()`)のキーを 1 つ抜く・足す・打ち違える・入れ替える。
     打ち違いはキーボードで隣のキー、母音どうし、音の近い子音(s/h、z/j/d、l/r、c/k)。足すのは母音、前後のキーの隣、
     同じキーの重ね。Mozc の既定のローマ字表でかなに直し、かなに直らないものは捨てる。打ったキーを読みに直した
     ものが今の読みと合うときだけ使う(かな入力や、途中で読みを直したときは、かなの書き換えだけ)。
   - かなの単位: 子音の打ち違い(同じ段のほかの行)、拗音の抜け(い段のあとの ゃゅょ)。
2. 選び方を変える。辞書のコストは、語に区切れなくなる書き換え(コストが 2000 を超えて上がる)を捨て、
   安い順に 80 個に絞るだけに使う。絞った読みは、LLM でかなのまま採点し、元の読みより点が上がったものを残す。
   書き換えた所の 4 文字後ろまでで切り、同じ所で切った元の読みと比べる(後ろは同じなので、計算がずっと少ない)。
   文字が増えた分は、元の読みの 1 文字あたりの点で埋め合わせる(つづき→つき のように、削るだけで点が上がるのを防ぐ)。
3. 複数か所を直す。点が上がった読みのうち上位 3 つから、次の 1 か所を直す(最大 3 か所、2 か所目からは 32 個)。
   2 か所目からは、それまでで一番よい読みより上がるものだけを残す。探し始めて 200 ms を過ぎたら次へ進まず、
   見つけた直しで文を作る。
4. 文を作って採るのは ADR0036 と同じ(zenz で生成し、zenz と LLM の点が元の文より 5 以上高ければ直す)。
   例外として、ず/づ・じ/ぢ の書き分けだけを直す読みで、かなのままの点が 6 以上上がったときは、差が 1 以上で直す。
5. 試すかどうかは、これまでどおりかなの 1 か所の書き換えだけで決める(選んだ文が自然で、辞書のコストも大きく
   下がらなければ試さない)。キーの書き換えまで含めると、どれか 1 つは辞書のコストが大きく下がり、
   自然な文(また今度遊ぼう、請求書、息が合う)まで試して別の語に変えてしまった。
6. 手が止まった間の裏の計算でも打ったキーを使えるよう、裏の仕事に打ったローマ字を写す。採点は 16 列ずつにし、
   前置きの計算は Space で止められるようにする(Space を待たせるのは、走っている採点 1 回分まで)。
7. キーの単位・複数か所の探索は、手が止まった間の裏の仕事でだけ行う。その場の変換(変換器を直接呼ぶ経路)で
   行うと、Space を押した後に数百 ms の探索が走る(日常の文で Space の p95 が 139 → 430 ms になったのを
   v3.1.0 の準備中に見つけて直した)。
8. Space を押してから変換を始めたとき(手を止めずにすぐ押した)も、打ち間違いの補正だけは、かなの 1 か所の
   書き換えの軽い補正を 200 ms まで行う。v3.0.0 は Space を待っている間の補正をすべて省いていたため、打ち間違い
   40 問はすぐ押すと 4 問しか直らず(手を止めると 24 問)、打ち直すと直る「たまに外れる」の原因になっていた。
   補正の関所は自然な文を通さないので、ふつうの文の正解数は変わらない。手が止まった間に深く探している途中で
   Space を押されたときは、これまでどおりすぐやめる。

`KOTORI_LM_TYPO_KEYS=0` で ADR0036 のとおりに戻る。調整用の環境変数は `mozc/README.md` の一覧に足した。

## 結果(RTX 3060、Standard、`mozc/tools/session_eval.py`、製品と同じセッションの経路)

手を止めてから Space を押したとき(すぐ押したとき・0.15 秒後は検証記録)。

| 評価セット | v3.0.0 と同じ動き | この変更 |
| --- | ---: | ---: |
| 利用者の 5 例 | 0 / 5 | 3 / 5 |
| 打ち間違い(kotori-typo) | 17 / 40 | 24 / 40(すぐ押すと 4 → 16) |
| 日常(kotori-daily) | 79 / 81 | 79 / 81 |
| 短文(asteria-short-dev) | 118 / 120 | 118 / 120 |
| 同音語(kotori-homophone) | 38 / 40 | 38 / 40 |
| AJIMEE(前文あり) | 187 / 198 | 187 / 198 |

全セット・全タイミングで、正しかった文を変えたものは 0。5 例で直せたのは、抽出・失礼・続き。打ち終わってから 2 秒手を止めると
お迎えも直る(4 / 5)。今日学校に… は、「がっく(学区)」が実在の語で辞書でも LLM でも見分けにくく、さらに「と」の
抜けがあり、直せない。速さと負荷試験は検証記録。

## 受け入れた不足(利用者の判断、2026-10-26)

- 5 例のうち直せるのは 3 例(条件は 4 例)。
- 打ち間違いのある文では、補正を探している間に Space を押すと、走っている採点 1 回分(十数〜数十 ms)待つ。
- すぐ Space を押したときの軽い補正のため、関所を通る文では Space の待ちが少し延びる(数値は検証記録)。
  精度と「たまに外れる」をなくすことを優先した(2026-10-27 利用者の指示「IME の最適化は、精度が下がる不具合や
  たまに外れる原因をなくすことを優先」)。

## 次の手

- 補正を、打っている間(手が止まるたび)に少しずつ進め、Space の前に終える。
- 抜けたかな(と・て・に など)の挿入は、辞書のコストで候補を絞れないので、別の絞り方が要る。
- 1 回の採点で扱える列の数(32)を増やせるか、ほかの採点への影響と合わせて測る。
