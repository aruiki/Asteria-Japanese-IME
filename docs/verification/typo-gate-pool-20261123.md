# 打ち間違いの補正: 試す条件と採点する数(Phase 3 の 1 段目、2026-11-23)

カード 96。v5.2.0〜v5.3.0 で kotori-typo 28/40・キー単位 2/5 のまま変わっていなかった。

## 外れの原因(KOTORI_LM_DEBUG・KOTORI_LM_TYPO_TRACE)

1. **試す前に外れる**: 選んだ文の読み 1 文字あたりの点が -1.8 より良いと試さない。長い文の 1 文字の誤り
   (おはよございます −1.74、へんこうしまいた −1.73、くだしあ −1.55)は文全体の平均で薄まる。
2. **採点の前に切られる**: 書き換えた読みを辞書で区切ったコストの低い順に 80 件だけ LLM で採点する。正しい読みの
   コストが元より高いことがある(へんこうしまいた 19,424 → へんこうしました 20,781)。同じコストの書き換えが多いと 80 件に入らない。

## 変更

`typo_gate_` -1.8 → -1.5、`typo_pool_` 80 → 160(`lm_rewriter.h`)。環境変数(KOTORI_LM_TYPO_GATE・POOL)で戻せる。

## 2 段目: 同じかなの重ね(2026-11-24)

`KOTORI_LM_DEBUG` に仮説ごとの文と点を出す行(`[typo]   hyp`)を足して、残りの外れを調べた。

- **おりまます**: 正しい文「お世話になっております」の点がいちばんよい(−14.07)のに、「ま」の余分をキー 2 つの余分として
  ほぼ起きない(−14.78)とし、負けていた。同じかなを 1 つ余分に打ったときは 1 回の余分なキー(Dhakal らの率)と見る
  (`KanaSlipLogRatio`)。kotori-typo 32 → 33/40、正しく打った 941 問の誤補正 0、時間は不変。
- 設定では直らない(K 10→40、探す時間 200→600 ms、幅 4→12 で同じ 32/40)。原因は LLM の点の不安定さ:
  - わかりまいた: 幅を広げると「わかりました」も比べるが、文脈なしの短い文で TinySwallow が「かかりました」(−11.16)を
    「わかりました」(−22.71)より大きく上に見る。
  - よやくお → を、ごかくいん → 確認: 正しい読みが、かなのまま LLM で採点して絞る段階で残らない。
  - けんとしておきます: 正しい文を見つけるが、LLM の差 3.45 が打ち間違いの起こりやすさ(−4.83)に届かず事後確率 0.196。
  - でんしゃがおくれていまう: 「遅れています」−25.04 と「遅れてしまう」−24.30 が僅差で、誤った方を採用する。
- 次の段は、かなのまま LLM で採点して絞る部分を、genmai の変換の点で絞る形に変えられるかを調べる(ロードマップ 3-2)。

## 3-2・3-1 を調べて見送った(2026-11-24)

- **3-2(かなのまま LLM で採点して絞る段を genmai の点にする)**: 残りの外れ 7 問のうち、絞る段で正しい読みが消えるのは 2 問
  (よやくお・ごかくいん)。3 問は正しい読みが最後の比較まで残り、文脈のない短い文の LLM の点で負ける(わかりまいた・
  けんとして・おくれていまう)。genmai の点は「その読みのときの文の確率」で、読みどうしの比較には使えない。読みごとに漢字の文へ
  変換して LLM で採点すれば効くが、160 件では数百 ms 以上かかり、効く見込みは 40 問中 2 問。
- **3-1(トークンごとの確率で誤りの場所を探す)**: 選んだ文のトークンごとの log P を読みの文字に割り当てて(実験のコード、製品には
  入れていない)、正しく打った 354 文(短文・日常・AJIMEE)と打ち間違いの 36 文で比べた。最小のトークンは多くが文の先頭(文脈の
  ない文の最初のトークンは何でも予想しにくい)。先頭の単位を除いても、-8 未満は正しい文 30%・打ち間違い 50%、-10 未満は 12%・28% で、
  試す条件にも場所の特定にも足りない。
- どちらも、文脈のない短い文での TinySwallow の点の不安定さが壁。実入力では前の文があるので、誤変換の報告で集まる実例で見直す。
