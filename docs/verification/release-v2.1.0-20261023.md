# v2.1.0 候補の検証記録（2026-10-23、ローカル）

GitHubが停止中(2026-10-22から403)のため、CI・Release・公開はしていない。この記録はローカルでビルドした候補MSIと、
ローカルで実施した評価・実機検証の範囲を示す。公開後のCI・資産照合は別途行う。

## 方針（利用者との合意、GOAL.md 2026-10-22）

製品の価値は変換精度。対象は日常の短文・仕事の文書・技術/専門用語・固有名詞/新語の4分野。測り方を製品の実際の
動作に合わせ、効果を測れた変更だけを入れる。

## 測り方の見直し（今回の主な発見）

- これまでの評価（AJIMEE 94%など）は `converter_main` の評価専用モード `KOTORI_LM_PRELOAD=0` で測っていた。
  このモードは同期読込に加えてLLM補正を止める（`identify_correction_models_ = !sync_load_ && …`）。
  非同期読込のCLIはAIの結果を待たずMozc単体の出力になる。いずれも製品のセッション処理とは経路が違う。
- 実際のIMEと同じセッション経路で評価する `mozc/tools/session_eval.py` を追加した。問ごとに打鍵→取り直し→Space→
  AIの結果待ち→表示文を記録→Escで取消（学習しない）。前文はすべてのキーに周囲文として付ける（実TSFと同じ）。
- 公開コーパスから4分野の評価セットを自動生成する `mozc/tools/build_eval_sets.py` を追加した。出典はzenz-v2.5の
  学習データ（2024年2月Wikipedia、CC-MAIN-2023-40）と重ならないもの: RealPersonaChat・JMultiWOZ（CC BY-SA 4.0）、
  ウィキニュース（CC BY 2.5）、2024年3月以降に作られたWikipedia記事3,027件（CC BY-SA 4.0、API取得）。
  読みはSudachiとUniDicの一致した文だけ採用（人手確認なし）。開発用300問・判定用500問/分野、文書単位で分割。
- 実際の文では正解の表記が書き手の好みの1つに過ぎない（見たり/観たり、わかる/分かる）。完全一致と並べて、
  Sudachiの正規化表記が一致すれば正解とする「表記ゆれ一致」を報告する（`mozc/tools/lenient_score.py`）。
  この規則は開発用セットの外れを見た後に定めた。判定用セットにはこの規則を固定して一度だけ使う。

## 変更

1. 数字の後の句読点: Mozcの `TransformCharactersForNumbers` は「前後とも数字なら、を，に」とコメントしながら
   前だけを見ていた。「賛成96、反対3」「電話番号は…298、最寄り駅は」の読点や文末の「96。」まで全角カンマ・ピリオドに
   なっていた。後ろの文字も確かめる。「1,000」「3.5」は従来どおり。composer/session の試験期待値を更新。
2. 数字の後の「パーセント」: zenzは読みどおりのカタカナを強く好み（90パーセント zenz -3.82/llm -15.60、
   90% zenz -9.29/llm -12.05）、LLMが「90%」を選んでも固定重みの合算で負けていた。文全体の採点後、数字の直後の
   「パーセント」だけが「%」「％」と違う採点済み候補があれば記号を選ぶ（`PreferPercentSymbol`、単体試験2件）。
3. 設定画面: 品質の説明に出していた正確さの数値（評価専用モード・AJIMEEのみで測定）を外した。
4. 版: BUILD 6443→6444。

## かなが自然な語の漢字化の改善（採用、6445）

指針「表記は日常で多い方」（GOAL.md 2026-10-23）に従った変更。

- 使用比率: `mozc/tools/build_kana_preference.py`。RealPersonaChat と JMultiWOZ のうち評価セットで開発用に割り当てた文書
  (234,589発話、判定用の文書は数えない)をSudachi(C単位)で区切り、正規化表記・読み・品詞が同じ語の表層ごとに数える。
  読みの違う表層(良い[よい]/いい)も同じ語として数える。漢字を含む少数派の表層 → 多数派の表層の組と多数派の割合を出す
  (良く→よく 0.969、殆ど→ほとんど 0.965、下さい→ください 0.901、良い→いい 0.878、後→あと 0.869)。表SHA 92d9368d…。
  多数派の割合0.7以上(事前に固定)の605組を `rewriter/kotori_notation_table.inc` に生成(`gen_notation_table.py`)。
- 製品: 文全体の候補それぞれについて、少数派の表層を多数派へ置き換えた文を作る(前後が漢字なら語の一部として置き換えない。
  「最後」「ご確認下さい」は変えない)。置き換えた文が読みに合う(MatchesReading)ときだけ、それを候補に加えて zenz/LLM で
  採点し(最大4件、LLMの採点対象にも入れる)、元の候補を 重み×Σlog(割合/(1−割合)) だけ減点する。読みに合わない組
  (今日は→こんにちは、よい→いい)は使われない。重み `notation_weight_`=0.5(調整前の既定値、KOTORI_LM_NOTATION_WEIGHT)。
  試験2件追加(置き換え、語の内部と前が漢字の語は置き換えない)。
- 開発用(セッション経路、5分野): 重み0.25/0.5/1.0のいずれも総合スコアは不変か微減(89.02→89.02/88.97/88.92)。

  効果(後→あと、因みに→ちなみに、又は→または)は点数に出ない。点数に出るのは読みの違う組(良い/いい)だけで、開発用には
  ほとんどなかった。副作用として固有名詞の表記変化(喫茶→きっさ、ウルテロン→裏テロン)を確認。
- 判定用(各分野1回、重み0.5): 総合 89.82→90.00、正解に変わった6・誤りに変わった2、最大の分野低下0.0。

  改善例: ちょうど良い→いい、どこか良い→いい、安いと良い→いい。誤り: どの辺り→どの辺、固有名詞の文1件。
- 注記: この規則を考える前に、Google比較で判定用の短文に「良い」の誤りがあることを見ていた。改善の幅は小さく、
  開発用では効果が見えなかった。表は会話コーパス由来で、百科事典的な文では口語寄り(一つ→ひとつ)になり得る。

## 次の改善の検証（2026-10-23、開発用セット）

### (0) Spaceから候補表示までの時間の基準

`mozc/tools/session_eval.py` に、Spaceを送ってからAIの結果が届いて候補が表示されるまで（サーバーが返す間隔で
KOTORI_REFRESHを送る、製品のTIPと同じ取り方）の時間を記録する機能を足した。6445相当のsession_handler_main
（notation-native-v1）、6445のモデル、RTX 3060。原票 `target/accuracy-guide/eval-sets-v2/results/latency-6445/`。

| 打ち方 | セット | 正解 | 中央値 | p95 | 最大 |
| --- | --- | --- | --- | --- | --- |
| 打ち終わって取り直しを待ってからSpace | short-dev | 231/300 | 4ms | 425ms | 946ms |
| 同上 | doc-dev（前文あり） | 252/300 | 104ms | 543ms | 1074ms |
| 打ち終わってすぐSpace（--immediate-space） | short-dev | 231/300 | 617ms | 1024ms | 1257ms |
| 同上 | doc-dev（前文あり） | 252/300 | 664ms | 1163ms | 1712ms |

**6445自体がp95 150msの基準を満たしていない。** 入力中に先に計算が終われば待ちはほぼないが、すぐSpaceを押すと
AIの生成・採点の時間（中央値約0.6秒）がそのまま待ちになる。

  doc 731ms（6445の 425ms / 543ms より遅い）。原票 `results/latency-unreal/`。**不採用**: p95が150msを超え、
  6445より遅い。精度の差は+2問（doc）で判定用セットへ進める根拠にならない。

### (3) ログイン時の常駐

ログイン時の読み込みは既にあった（MSIがHKLMのRunへ `Kotori Prelauncher` を登録し、`mozc_broker --mode=prelaunch_processes`
がサーバーを起動、サーバーは起動時に裏でモデルを読み込む）。一方、10分入力がないとモデルを外す既定（ADR0034）が残っており、
AIの結果を待つ方式（ADR0067）では、外れた後の最初の変換が読み込み直しを待っていた。既定を「外さない」に変えた（ADR0069、
ag16 401688515）。`KOTORI_LM_IDLE_UNLOAD`（秒）を指定したときだけ外す。

`mozc/tools/first_conversion.py`（session_handler_main、「きょうはいいてんきですね」を打ってSpace、各3回、RTX 3060）。
変更前は6445相当（notation-native-v1）。放置の場面は、変更前の既定（10分で外す）を `KOTORI_LM_IDLE_UNLOAD=5` と45秒の放置で再現した。
原票 `target/accuracy-guide/first-conversion-v1/`。

### (5) 導入検査の後に学習履歴を戻す

`mozc/tools/local_install_check.py` の実入力の段階（verify/clickprobe/browser）は、入力の直前にサーバーを止めて利用者の
プロファイルを保存し、終わったら成否にかかわらず戻して、全ファイルのSHA一致を `<段階>_profile` として記録する。
一致しなければ段階を失敗にする。試験 `mozc/tools/test_local_install_check.py`（書き換え・追加・削除・読み取り専用の
履歴を戻す、失敗した検査でも戻す、不一致を失敗にする）3件合格。サーバーを止めた時点でまだ書き出されていない学習は
保存に入らない。このPCでの実行はしていない（導入は今回の範囲外）。

## 速度の改善（2026-10-24〜、ゴール「爆速で精度の高いIME」）

### 時間の内訳を測る道具

- サーバー: `KOTORI_LM_TIMELINE=1` で、AIの変換1回ごとに、仕事を積んだ時刻・計算開始（ロック）・生成・zenz採点・LLM採点・
  終了（補正・文節分け・保存）の時刻を steady_clock のマイクロ秒で stderr に出す（入力文は出さない）。
- 評価: `mozc/tools/session_eval.py --timeline` が Space を送った時刻（perf_counter、同じQPC）と突き合わせ、問ごとに
  before_space（Spaceの前に済んだ計算）/ queue（積んでから計算開始まで）/ gen / zenz / llm / finish / pickup（計算の終わり
  から表示まで）を出す。
