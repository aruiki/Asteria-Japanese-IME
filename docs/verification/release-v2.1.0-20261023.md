# v2.1.0 候補の検証記録（2026-10-23、ローカル）

GitHubが停止中(2026-10-22から403)のため、CI・Release・公開はしていない。この記録はローカルでビルドした候補MSIと、
ローカルで実施した評価・実機検証の範囲を示す。公開後のCI・資産照合は別途行う。

## 方針（利用者との合意、GOAL.md 2026-10-22）

製品の価値は変換精度。対象は日常の短文・仕事の文書・技術/専門用語・固有名詞/新語の4分野。測り方を製品の実際の
動作に合わせ、効果を測れた変更だけを入れる。

## 測り方の見直し（今回の主な発見）

- これまでの評価（AJIMEE 94%など）は `converter_main` の評価専用モード `KOTORI_LM_PRELOAD=0` で測っていた。
  このモードは同期読込に加えてLLM補正を止める（`identify_correction_models_ = !sync_load_ && …`）。
  非同期読込のCLIはAIの結果を待たずMozc単体の出力になる。いずれも製品のセッション処理とは経路が違う。
- 実際のIMEと同じセッション経路で評価する `mozc/tools/session_eval.py` を追加した。問ごとに打鍵→取り直し→Space→
  AIの結果待ち→表示文を記録→Escで取消（学習しない）。前文はすべてのキーに周囲文として付ける（実TSFと同じ）。
- 公開コーパスから4分野の評価セットを自動生成する `mozc/tools/build_eval_sets.py` を追加した。出典はzenz-v2.5の
  学習データ（2024年2月Wikipedia、CC-MAIN-2023-40）と重ならないもの: RealPersonaChat・JMultiWOZ（CC BY-SA 4.0）、
  ウィキニュース（CC BY 2.5）、2024年3月以降に作られたWikipedia記事3,027件（CC BY-SA 4.0、API取得）。
  読みはSudachiとUniDicの一致した文だけ採用（人手確認なし）。開発用300問・判定用500問/分野、文書単位で分割。
- 実際の文では正解の表記が書き手の好みの1つに過ぎない（見たり/観たり、わかる/分かる）。完全一致と並べて、
  Sudachiの正規化表記が一致すれば正解とする「表記ゆれ一致」を報告する（`mozc/tools/lenient_score.py`）。
  この規則は開発用セットの外れを見た後に定めた。判定用セットにはこの規則を固定して一度だけ使う。

## 変更

1. 数字の後の句読点: Mozcの `TransformCharactersForNumbers` は「前後とも数字なら、を，に」とコメントしながら
   前だけを見ていた。「賛成96、反対3」「電話番号は…298、最寄り駅は」の読点や文末の「96。」まで全角カンマ・ピリオドに
   なっていた。後ろの文字も確かめる。「1,000」「3.5」は従来どおり。composer/session の試験期待値を更新。
2. 数字の後の「パーセント」: zenzは読みどおりのカタカナを強く好み（90パーセント zenz -3.82/llm -15.60、
   90% zenz -9.29/llm -12.05）、LLMが「90%」を選んでも固定重みの合算で負けていた。文全体の採点後、数字の直後の
   「パーセント」だけが「%」「％」と違う採点済み候補があれば記号を選ぶ（`PreferPercentSymbol`、単体試験2件）。
3. 設定画面: 品質の説明に出していた正確さの数値（評価専用モード・AJIMEEのみで測定）を外した。
4. 版: BUILD 6443→6444。

## 既知の問題（今回は直さない）

- （訂正）「18か→18課」は製品の不具合ではなく、評価データの読みの誤り。「18日」の読みは「じゅうはちにち」で、
  評価セット生成時に数字と「日」を別々に読んで「18か」という不自然な入力ができていた。AIはその入力からも「日」を
  選んでいた。数字＋助数詞の読みは評価セット生成器の改善点（次の版で直す）。
- 「注射/駐車のアシスト」「ラップ/聞かない」等、文の意味で決まる同音語の誤り。両モデルの知識不足で、重みでは直らない。
- 固有名詞は4分野で最も弱い（表記ゆれ一致 78%）。
