## 文を作り直す LLM の補正を変換で使わない
カード 89 で Space を待っているときも補正を最後まで行うようにしたところ、文脈の選択の p95 が 87 → 458 ms に延びた。
内訳を見ると、延ばしていたのは文を作り直す LLM の補正(`FindLlmCorrection`)で、どのセットでも正解を増やしていない。
変換では使わない(開発で `KOTORI_LM_CORRECTION=1` のときだけ)。打ち間違いの補正は残し、設定「入力中に誤変換を補正する」に従わせた。

## 設定画面からの受け取り・削除(開発用の木の mozc_tool、本物の WebView2 の画面、2026-11-04)
WebView2 にデバッグ用の窓口(`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port`)を開け、playwright で画面の
ボタンを押した(押す・確認の窓・進み具合は利用者と同じ)。保存先は利用者のプロファイルの `models`。

| 操作 | 結果 |
| --- | --- |
| High の受け取り | 0 → 73 → 100%、127 秒。`.part` から本来の名前へ。4018918816 バイト、SHA-256 64e16e94…8c2c(表と一致) |
| Unreal の受け取り | 128 秒。4920735136 バイト、SHA-256 292a4e26…4277(表と一致) |
| 品質の選択 | 入っている段階だけ選べる(入っていない Unreal は選べない)。選ぶと「保存しました」、設定の品質が変わる |
| Unreal を選んだまま削除 | ファイルは消え、設定は Standard に戻ったが、**画面は「入っています」のまま、品質も Unreal のまま、「消しました」が出ない** |

原因: 画面は要求ごとに番号(`id`)を付けて返事を待つが、受け取り・取り消し・削除ではモデルの名前も `id` で送っていた。要求の番号が
上書きされ、返事の番号が -1 になって画面が返事を受け取れなかった(5.0.0 から。受け取りは完了の知らせで画面が更新されるので
表に出なかった)。モデルの名前を `model` で送り、要求の番号を引数で上書きしないようにした。直した後: High を選んだまま削除すると、
画面は「ダウンロード」に戻り「消しました。」が出て、品質は Standard。もう一度受け取れる(80 秒、SHA 一致)。

## 導入した MSI での判定役(run 41749453963、MSI 2baacbe4…d792、3.34.6489.100)
利用者の PC に導入し、入れた版の設定画面で High を選び、実入力(`installed_probe.py`、本物の TSF)で変換した。
AI の状態に `judge=llama-3.1-swallow-8b-v0.5-q3_k_m.gguf` が出て、GPU のメモリが約 3.5 → 7.5 GB に増えた(判定役の分)。
読み込んだ後の変換は正しい(茶道いいですね、空間光変調器、精度が低すぎる、打ってる途中でも、ないと、明日の会議は１０時からです)。

**見つけた問題**: 最初の 2 問(あついほん、じしんがあった)は、確定の時刻(Space の 2 秒後)までに変換が出なかった。判定役(4〜5 GB)を、
標準のモデルと同じ裏の仕事の係で、変換の鍵を握ったまま読み込んでいたため。起動のたび・休んで戻るたびに、最初の変換が数秒待つ。

直したこと: 変換の処理では判定役を読み込まず、読み込みは専用のスレッドで変換の鍵の外で行い、読み終えてから差し込む。読み込みの間は
判定役なしで変換する。評価(その場で読み込む設定)では、これまでどおりその場で読む。

開発用の木で、起動直後から打ったときの変換(打鍵を含む):

| | 1 回目 | 2 回目 | 判定役を読み込んだ後 |
| --- | ---: | ---: | ---: |
| Standard(判定役なし) | 2265 ms | 557 ms | 261 ms |
| Unreal(鍵を握って読む・係で読む) | 2266 ms | 2268 ms | 260〜456 ms |
| Unreal(専用のスレッドで読む) | 2183 ms | 1133 ms | 263〜453 ms |

1 回目はどれも標準のモデルの読み込み。2 回目の残りの差は、判定役を GPU に送っている間の計算の取り合い。設定を Unreal に切り替える
SET_CONFIG は 3〜32 ms、直後の打鍵は 1 ms で、切り替えで止まることはない。
