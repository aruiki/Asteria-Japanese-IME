- 対象: PR206(Issue #205)。Mozc の作業ツリー ~/ag16 の枝 asteria/hide-suggestion-window(BUILD 6463 + この変更)。
- 環境: このPC(RTX 3060 12 GB、Windows 11)。モデルはインストール済みの v4.1.0 と同じ(`C:\Program Files (x86)\Asteria`)。
- 道具: `mozc/tools/session_eval.py --context`(実際の IME と同じセッションの経路)。窓ありは
  `--config kotori_hide_suggestion_window=false`、窓なしは既定。Space のタイミングは、手を止めて(既定)・`--space-gap 150`・

## 1. 窓あり・なしで Space の結果が変わらないこと

### 最初の作り(入力中の候補を作らない)で見つけた違い

- 打ち間違い(40)・手を止めて: 窓あり 23、窓なし 22。「らいねんのけいかう」が 来年の計画 → 来年の経過う、
  「しんかんせでかえります」が 新歓 → 新刊(4 回くり返して 4 回とも同じ)。打鍵ごとの候補作り
  (`LmRewriter::RewriteSuggestion`)が AI の先回りの変換と打ち間違いの補正を始めさせていたため。
- 起動して最初の問だけ、窓なしで Space が約 0.18 秒待った(3 回とも 177〜179 ms、窓ありは 3 ms)。取り直しの時間
  (`kotori::g_live_first_ms`)が打鍵ごとの変換の要求(`LmRewriter::Touch`)でしか決まらず、最初の入力で取り直しの予約が
  出なかった。モデルの読み込みのときにも決めるようにした(`LmRewriter::UpdateLiveTiming`)。

## 2. 窓なしで見えない候補をキーで確定しないこと

- 単体テスト `KotoriDefaultHidesSuggestionWindowButKeepsAiForSpace`・`KotoriHiddenSuggestionIsNotCommittedByKeys`
  (Shift+Enter は何もしない、Ctrl+Enter は打った読みのまま確定)。

## 3. セッションの経路での乱打

- 道具: 音節単位の打鍵・Caps Lock・Backspace・Space・Enter・Esc・Tab・↓・Shift+Enter・Ctrl+Enter・F7・F10・半角/全角と、
  間を置いた取り直しを乱数で混ぜる(`mozc/tools/session_fuzz.py`)。窓なしで、打鍵・取り直しの直後に
  入力中の候補の窓(category: SUGGESTION)が出たら違反とする。窓ありで同じ検出が働くことを先に確かめた。
- 結果(各 1500 回、計 7500 回): すべて落ちなかった。同じ乱数(種 2)で、窓ありは打鍵・取り直しの直後に窓が 4 回出て、
  窓なしは 0 回。ライブ変換(種 3)・英語の名前(種 4)・両方(種 5)でも窓なしの違反 0。

## 4. 10/28 の異常終了の記録(query_of_death.log)

- このPCに、開発版 6461 で IME のサーバーが落ちた記録があった。Caps Lock を入れたまま英語の名前を打ち、Space の後の
  取り直しの最中に落ちた。356 の操作をそのまま流し直す道具(`mozc/tools/qod_replay.py`)で、今の版を既定・ライブ変換・英語の名前・
  すべてオン(窓あり)の 4 通りで試し、すべて落ちなかった。v4.1.0 で、Caps Lock のときに打ったキーを小文字にしてから
  英語の名前を探すようにした変更(ag16 121b73e67)と合う。

## 5. 応援のお願いの通知

- 原因: 一度も通知を出していない AUMID では `ToastNotifier.Setting` が 0x80070490(見つからない)を返す
  (PowerShell で新しい AUMID を作って再現)。それを失敗として扱い、表示の前に止めていた。先に3日後へ延ばしていたので、
  3日ごとに同じ失敗をくり返していた。このPCでは Windows の通知の登録(`HKCU\...\Notifications\Settings\Aruiki.Asteria.Support`)
  が一度も作られていなかった。
- 修正の確認: 直した `mozc_tool --mode=support_reminder` を、予定を過ぎた状態で起動して、通知センターに届き
  `last_result=0x00000000` と3日後の予定が残った。単体テスト 11 件。
- AppContainer(隔離された環境)から起動されたときは、直す前の版もすぐ終わり、排他を持ち続けることはなかった(試験用の
  AppContainer で確認し、試験の後に消した)。パッケージのアプリ(Claude など)から起動されたときは保存先が仮想化され、
  別の記録で2つ目の常駐が動く(Claude の仮想フォルダーに旧 Kotori の記録が残っていた)。そのときはすぐ終わるようにした。
