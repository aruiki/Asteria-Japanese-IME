# KanaAI 精度改善・目標再定義の技術指南書

作成日: 2026-10-16

## 本書の位置づけ

ユーザーの問題提起は「AIとGPUに大きな資源を投じているのに、ほぼ誤変換しない品質に到達していない」である。本書はこの要求を製品目標、技術課題、検証条件へ翻訳する設計上の提言である。実装変更は行わない。

今回は実行環境が `MXC launcher: enumerate MXC volume Y:` の認証エラーで起動せず、代替のファイル読み取りもタイムアウトした。現行GOAL、STATE、コード、測定結果は確認できていない。したがって、以下の技術課題は調査・改善すべき項目であり、現在の実装に欠陥が存在すると断定したものではない。ユーザー提示のAGENTS.mdを設計上の制約とする。本書だけで既存の完成条件や公開条件を変更しない。

## 1. 目標の正しい解釈

**目標はAIやGPUを使うことではなく、利用者が意図した文章を、少ない修正で、待たずに確定できることにある。** AIとGPUはそのための手段であり、使用率、モデル規模、プロセス稼働、推論成功件数は品質の達成指標ではない。

「100%に近い精度」を諦める必要はない。ただし、どの入力を、どの文脈で、何を正解として採点するかを固定しなければ、この数字は設計を導かない。同じ読みが複数の表記を許す場合、読みだけから本人の意図を一意に復元することはできない。評価では次の二つを分ける。

- 文脈から正解が定まる入力: 第一候補の正答率を厳しく測り、誤りを減らす。
- 複数の表記が妥当な入力: 許容表記集合と候補到達性、選択・修正の手間を測る。単一参照文との不一致をすべて誤変換扱いしない。一方、本人が望んだ表記への到達コストは残す。

ここでの目標修正は合格を容易にするためではない。**測れない万能精度から、失敗が見え、改善が製品に反映される目標へ置き換える。**

## 2. 修正すべき目標解釈

| 誤った解釈 | 採用すべき判断基準 |
|---|---|
| 大型モデルとGPUを使えば高精度になる | 増分の計算資源が、どの誤変換を何件減らしたかで採否を決める |
| 自然な文章なら正しい変換である | 読み、意味、固有名詞、数字、文体、本人の意図を保持する |
| AIが応答したのでAI機能は完成した | 応答が対象入力の候補へ期限内に反映され、確定操作まで寄与したことを確認する |
| 平均正答率が高ければ完成である | 日常語、専門語、名前、短文、長文などの弱い層と重大誤変換も判定する |
| 辞書の正解をAIが選べば十分である | 正解候補が存在しない問題と、存在するのに選べない問題を別々に解く |
| 推論を毎回動かすほど賢くなる | 必要な入力だけに計算資源を配り、入力応答性と総修正量を改善する |
| 評価データで高得点なら実用でも高精度である | 未知の文・利用者・分野と、実際の入力途中の動作で再確認する |

## 3. 最優先の技術診断: 誤変換の発生段階を分解する

最初にモデル交換を行わない。固定した誤変換事例について、次のどこで失敗したかを記録する。

1. 読み・分節: 読みの正規化や区切りが適切だったか。
2. 候補生成: Mozcの候補または探索対象に正解表記が存在したか。
3. 順位付け: 正解が存在したのに低く評価されたか。
4. 文脈: 必要な情報が不足、古い、または誤っていたか。
5. 配送・反映: AI結果が遅延・破棄・世代不一致などで実際の候補に届かなかったか。
6. 表示・確定: 表示した候補とSpace・Enterで選ばれる候補が一致したか。
7. 正解定義: 表記揺れや曖昧さを誤って不正解にしていないか。

これらは併発しうる。主原因と副原因を残し、代表例だけでなく件数を集計する。最大の誤り群に対して改善を選ぶ。

## 4. 中核となる具体的改善

### P0: AI結果が実際に使われることを証明する

候補生成、要求投入、推論終了、結果受領、世代検査、候補反映、表示、確定を一つの要求IDで追跡する。本文を通常ログへ無制限に保存せず、診断用の同意された入力で再現する。

同じ読み・確定済み文脈・辞書・履歴条件でAIのON/OFFを比較する。推論完了率だけでなく、期限内反映率、候補順位の変化、正解への改善件数、誤りへの改悪件数を測る。インストール済みバイナリとソースの対応、ハッシュ、実際に選択されたIMEも固定する。

この段階を通らなければ、モデルの精度評価と製品の精度評価は接続できていない。

### P1: 正解候補が存在しない問題を減らす

評価対象の正解が探索候補に含まれる比率を測る。純粋な候補並べ替えでは、第一候補正答率はこの比率を超えられない。

正解欠落が多い場合は、Mozcの辞書・ユーザー辞書・分節・候補探索幅を調べる。探索幅の拡大は全入力へ一律適用せず、曖昧な箇所を対象に遅延とメモリを測る。名前、専門語、表記の好みは、明示登録や確定結果に基づく個人適応も使う。

生成モデルによる新規候補は、そのまま確定文字列へ差し替えない。読みとの整合、数字・記号・固有名詞の保持を検査し、候補として提示する。候補IDの安全性と元候補への復帰を維持する。

### P1: 流暢さではなく変換の正しさを学習する

一般的な文章生成能力だけに依存せず、読み・許可された確定済み文脈・候補集合から、意図に合う候補を選ぶ課題として学習・評価する。

実際の誤変換から、正解候補と紛らわしい誤候補の組を作る。同音異義語、分節違い、助詞、送り仮名、固有名詞、数値、専門語を含める。単なるランダム誤候補だけでは難しい識別を学べない。

Mozcのスコア、読み整合性、文脈適合性、確定履歴に基づく個人傾向を組み合わせる。候補長などの偏りを確認し、重みは開発用データで決める。最終評価データを見ながら調整しない。

### P1: 自信のない変更を抑制する

モデルの自己申告の自信をそのまま使わない。候補間のスコア差やMozcとの不一致などが実際の正答率と対応するか、独立した較正用データで確認する。

AIが上位候補を変更する条件を設け、変更した範囲の正答率と変更対象の割合を同時に報告する。変更数を減らして見かけの成功率だけを高めない。Mozcが正しかった入力をAIが壊した件数を独立した重要指標にする。

### P2: GPUを誤り削減に効く場所へ配分する

全キー入力で大型推論を呼ばず、確定済み文脈の非同期処理、再利用可能な文脈表現、難しい候補の比較に計算資源を配る。CPUで動く軽量モデル、蒸留、量子化、キャッシュは、それぞれ精度と遅延の前後比較で採否を決める。

キャッシュには文脈・辞書・個人適応の更新を反映するキーや無効化条件を設ける。古い要求は取り消し、古い結果を新しい入力に適用しない。大型モデル、ディスクI/O、通信をキー入力の同期処理へ入れない。

AIが未起動、タイムアウト、異常終了してもMozc入力を維持する。CPUのみ、初回起動、低メモリ、即時Spaceでも確認する。GPU使用率の低下は、それだけでは改善と主張しない。

### P2: 個人適応を安全に積み上げる

本人が確定した表記、明示登録した語彙、許可された短い文脈を利用する。未確定候補やAI自身の出力を無条件に正解として再学習しない。誤学習を取り消せるようにする。

保護フィールドでは文脈取得・AI・学習を停止する。文脈を増やすほど良いとは限らないため、文脈なし・短い文脈・個人適応ありを比較する。

## 5. 精度目標と評価契約

「99%」という数値は暫定目標の例であり、現在の達成値でも合意済み合格基準でもない。対象範囲と評価単位を先に固定する。

| 指標 | 定義・用途 |
|---|---|
| 第一候補完全一致率 | 一つの変換要求について第一候補が正解集合に入る割合。文字単位の精度とは分ける |
| 候補包含率 | 決めた探索範囲に正解が含まれる割合。候補生成の限界を測る |
| 候補到達性 | 上位K件に正解がある割合。Kを明記する |
| 正味改善 | 同一入力のON/OFF比較で、改善件数と改悪件数を別々に報告する |
| 修正コスト | 固定した入力課題で、確定までに必要な追加操作数・訂正時間を測る |
| 重大誤変換 | 数字、名前、否定などの意味を変える誤りを分類し、件数と分母を報告する |
| 応答性 | 入力から表示までのp50/p95/p99、AI結果の期限内反映率を測る |
| 資源 | CPU/GPU、RAM/VRAM、初回起動時間をハードウェア条件と併記する |

99%の変換単位正答率でも、100回の変換が独立であると仮定すれば、全部正しい確率は約36.6%にとどまる。この計算は実際の独立性を主張するものではない。平均精度の数字と、長時間使ってほとんど困らない体験は同じではないことを示す。

評価データは日常文、業務文、専門語、固有名詞、曖昧語、長文、短文、未知語へ分ける。訓練用・調整用・最終評価用を分離し、類似文の漏洩を避ける。頻出入力の加重平均と、各層の値の両方を出す。高精度域では少数の例だけで判断せず、分母と信頼区間も示す。

モデル単体、オフライン変換、インストール済みIMEでの実入力の三段階を別々に判定する。単体テストやインストーラー成功は実入力精度の代替にならない。

## 6. 実行順序と成果物

1. 現行GOAL、STATE、リリース契約、検証記録、差分とコードを読み直し、本書の仮説と現物を照合する。
2. ソースコミット、成果物ハッシュ、モデル、辞書、ハードウェアを固定した基準測定を作る。
3. 誤変換を発生段階別に分類した台帳を作る。個々の例に正解根拠、原因、AI反映の有無を残す。
4. 最大の誤り群に一つの技術変更を適用し、同じ条件のON/OFF比較と未使用データで効果を確認する。
5. 正解候補欠落が支配的なら候補生成へ、順位誤りなら識別学習へ、反映失敗なら配送経路へ投資する。
6. 実際のアプリで表示、Space、確定、連続入力、AI障害時の動作を確認する。
7. 数字と未検証範囲を示した上でGOALの改訂案を作り、製品完成と公開の判定は既存契約に従う。

必要な成果物は、評価仕様、固定評価セット、誤変換台帳、再現可能な測定コマンド、改善前後の結果、実入力の検証記録である。モデルの交換やGPU増設だけを成果物としない。

## 7. GOALへの改訂提案文

> KanaAIは、Mozcの日本語入力を維持しながら、完全ローカルのAIにより利用者の意図に合う表記への到達を改善する。品質は、対象と正解定義を固定した未使用評価データの第一候補正答率、候補包含率、重大誤変換、AIによる改善・改悪、実入力の修正コストと応答性で判定する。GPU使用、モデル起動、推論成功だけでは達成としない。高精度を目指す数値目標は評価単位と対象範囲を明記し、曖昧入力を含む無条件の完全一致を約束しない。AIが利用できない場合も入力を継続でき、実際の候補表示と確定操作への寄与を検証する。

この提案を採用するときも、既存の保護フィールド、安全性、導入・削除、署名・配布段階、独立検証の条件を削除しない。数値閾値は基準測定後に決定し、結果を見て後から合格線を下げない。

**技術責任者の判断は、投入資源の大きさではなく、どの失敗を、どの仕組みで、どれだけ減らしたかを根拠にする。**
